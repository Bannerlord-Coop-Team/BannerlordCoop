# Granularity and evidence contract

One feature entry describes a player-visible action or capability. Keep success, refusal,
partial application, reward ownership and shared observations as outcome variants of that
entry. Add an individual source case when its guard, result or side effects need an independently
specified oracle. Do not create feature entries for every syntax branch or numeric input.

| Record | Purpose | What it establishes |
| --- | --- | --- |
| [catalog.csv](catalog.csv) | 385 behaviors in 31 areas, input surface, variants and required observation | a coverage question or named source surface, with its own support/status |
| [source-cases.csv](source-cases.csv) | 63 interpreted outcomes or boundary tables with parent behavior and complete-member spans | the stated member-level source result only; runtime is separately recorded |
| [baseline/installed.json](baseline/installed.json) | installed registrar, menu and perk definitions with owning DLL hash | definition/registration discovery, not compatibility |
| [baseline/behavior-sources.json](baseline/behavior-sources.json) | the eight complete source identities cited by the interpreted cases | source binding and span bounds, not a runtime result |
| on-demand `inventory` | command/argument/side, sync expression and Harmony declaration with file hash/line | lexical navigation requiring source/runtime confirmation |

The source cases retain input assumptions, expected result, state changes, side effects,
negative/boundary control, authority, support restriction, runtime status and remaining work.
Numeric wage, recruitment, clan-tier and upgrade-XP examples share calculation/boundary tables.
Each named input still needs its own expected/actual observation when that boundary is in scope;
one passing example cannot establish an entire table.

Catalog variants and oracles are acceptance requirements. A `candidate` is unresolved;
`source-inspected` identifies a repository surface without proving every method or branch.
All source-case rows are `source-interpreted`; the associated complete member supports only
the stated result. A model quote is not a completed payment, roster change or reward transaction.
Installed perk/menu records are definitions, not interpreted apply paths.

Runtime is independent: `unrun`, `blocked` or `exercised` applies only to the named action,
oracle, source/build and evidence. Support restrictions are also independent: normal issue
gates, disabled UI or optional module requirements survive source inspection and debug catalogs.
The current map contains no newly exercised gameplay case.

For a relevant change, expand only its material variants. Trace callers, preconditions, role,
thread/authority, object identity, RNG and indirect effects before predicting the production result.
For perks, follow [the inspection guide](perks.md), keeping choice and both effect paths distinct.
Re-inspect exact installed code when a claimed vanilla behavior is not already bound here.

The server is authoritative and has no playable hero or party. Drive a real player's action
from its client; perform authoritative debug setup on the server. Observe both real clients'
owner/observer state, required side effects and rendered UI when relevant. Persistence/reconnect,
interruption/repetition and reward ownership remain separate obligations when the change affects them.
Use [runtime](recipes/runtime.md) and the existing harness/report contract; preserve existing
owners, source receipts and Local/Remote lane. Map counts, compilation, CI, synthetic state,
a debug acknowledgment and one happy path cannot establish complete gameplay support.
