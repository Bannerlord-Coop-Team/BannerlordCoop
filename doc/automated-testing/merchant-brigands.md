# Merchant Needs Help With Brigands

The port uses `Issues/Framework` for creation, accept arbitration, per-player similar commitments, companion returns and finalization. The quest adapter owns bandit targeting, progress and the quest-specific consequence methods. It adds no duplicate-quest gate.

Source inspected: installed Native v1.4.8, `TaleWorlds.CampaignSystem.dll`, SHA-256 `1F8E33E2ED73E6EC653D7629180AFB70649DDC6E5BD1657A802A264EFDA1C3AE`. ## Pending live flows

Live testing is pending. Use the supervisor-assigned lane with a dedicated server and two real clients. Run changes on the server; inspect both clients. Start at Danustica (Southern Empire, settlement `town_ES1`, town `town_comp_ES1`). Use `coop.debug.hero.list` and `coop.debug.town.list_towns` to resolve the save's merchant, village notables and nearby infested hideout. The giver and target party identities must come from that save. The server command `coop.debug.issues.give` takes the resolved giver id followed by `MerchantNeedsHelpWithOutlawsIssue` and retains vanilla's suitable-hideout condition.

1. **Offer, decline and acceptance:** talk to an eligible merchant or rural notable through real dialogue. Declining keeps the issue available. Accepting gives only that client's journal, with the quoted target count, reward and 20-day limit; the server records its owner and keeps an unstarted mirror. Try insufficient troops, relation below -10, war with the giver and a no-longer-infested hideout. Vanilla eligibility and the framework must refuse them where applicable.
2. **Concurrent ownership:** each client accepts from a different giver. Both copies must coexist; a player already holding this type must be refused another copy. A race for the same giver must have one owner.
3. **Target changes and partial progress:** let bandits enter/leave the related hideout and move into/out of range. The server chooses patrol AI and targets. Only the owner sees its markers and progress. Another player's or an AI party's victory must remove the target without giving the owner credit. Repeated destruction notifications must not count twice.
4. **Defeat-only success:** fight the required brigand parties through the supported encounter and mission path. The server awards the quoted gold, +3 giver relation, +1 clan renown and +5 town security/prosperity. Only the owner receives the completed progress and defeat-only journal. Remaining target AI and markers are released.
5. **Recruitment success:** recruit qualifying parties through real bandit dialogue and the roster screen. Exercise both a mixture of victories/recruitments and recruitment-only completion. The owner gets the corresponding vanilla journal and one reward. Recruiting for the other player must give no credit to this quest.
6. **Companion accept/cancel and returns:** use the real companion/troop picker, including cancel and tier-2 troop eligibility. Check Tactics/Scouting failure-risk scaling and quoted duration. Exercise success and failure with casualties. The server resolves the result once, returns the surviving troops/companion to the owner, and applies the correct gold, relation, renown and settlement effects. Only the owner's journal displays the mission and result; the second client's party and personal quests stay unchanged.
7. **Companion return while busy:** let the return become due while the owner is in an encounter, captive or disconnected. It must wait without sending troops or rewards to another player, then complete for the same owner when return is possible.
8. **Timeout:** allow the personal quest to expire with partial progress. The server applies -5 giver relation and -10 town prosperity once; only the owner receives the failure log and ends its quest. Verify target cleanup.
9. **World cancellations/failure:** exercise a raid on a rural giver's village, a war caused by the owner (failure), an externally caused war (cancellation), a clan/kingdom change into war, and coercing a village related to the giver (failure). The server evaluates each event as the owner; the owner receives its reason and final state, while the other player's independent quest continues.
10. **Lifetime checks:** disconnect/rejoin while hunting and during a companion mission; repeat with the giver unavailable and the player becoming captive or dying. The current framework dismisses a disconnected player's personal quest and cleans its targets. Companion missions retain their recorded owner while that owner exists; missions with no surviving owner are dismissed. Verify those rules and vanilla issue lifetime, preserving valid party identities, cleanup and rewards. These paths have no live evidence yet.

There is no lord solution (`IsThereLordSolution == false`), and the quest adds no persuasion, bribery or quest-specific mission spawning. Its three personal success journals distinguish all defeated, mixed defeated/recruited and all recruited parties. Companion failure/success and the war/raid/coercion/timeout branches are separate checks.
